# Changelog

All notable changes to this project are documented in this file.

## 0.8.0 - 2026-09-27

Требования прежние: OpenClaw ≥ 2026.9.6, Node.js ≥ 22. Конфиг 0.7 работает без правок; что меняется при обновлении и как вернуть прежнее — в конце раздела.

### Added

- Пересланные сообщения доходят до агента: текст и описания вложений из `link.message`, включая пересылку без собственного текста, с автором и типом источника в штатных полях SDK (`ForwardedFrom*`). Собственный комментарий отправителя идёт первым; пересланный текст не разбирается как команда; вложения пересылки скачиваются после проверок доступа, с теми же лимитами.
- Цитата при ответе: агент получает текст исходного сообщения (до 1000 символов) и его автора (`ReplyToBody`, `ReplyToSender`); у сообщения без текста — типы вложений.
- Опция `actionScope` (`admitted` по умолчанию, `current`, `off`): в каких чатах инструмент `message` выполняет `send`, `sendAttachment`, `sticker`, `edit`, `delete`, `pin`, `unpin` (см. Security).
- Опции `notify` и `disableLinkPreview`: умолчания push-уведомлений и превью ссылок для всех отправок. Явное значение вызова сильнее: флаг `silent` ядра, затем `channelData.max.notify` / `silent` / `disableLinkPreview`. В каналы MAX тихая отправка не уходит — MAX принимает там только `notify = true`; тип чата узнаётся одним `GET /chats/{chatId}` с кэшем на процесс.
- Опция `mediaMaxCount` (по умолчанию 12): сколько медиавложений скачивается из одного входящего сообщения вместе с пересланными; об остальных агент получает пометку.
- Входящие контакты, геолокация и share-карточки описываются агенту разобранными: имя и телефоны из VCard и профиль MAX (без сырого `vcf_info`); координаты и ссылка на карту; заголовок, описание и ссылка.
- `heartbeat.sendTyping` и `sendTypingGuarded`: индикатор набора для heartbeat-ходов, ходов из gateway и прогресса фоновых задач.
- Опция `httpProxy`: HTTP(S)-прокси для всех запросов плагина к MAX — Bot API, загрузки на upload-адреса, скачивание входящих вложений и медиа по ссылке (через `dispatcherPolicy` ядра, SSRF-проверки сохраняются). TLS до MAX проверяется внутри туннеля тем же набором CA, включая сертификат Минцифры; учётные данные прокси не попадают в логи и ошибки; `""` у аккаунта отключает унаследованный прокси; loopback-адреса идут мимо прокси.
- Опция `apiBaseUrl`: свой адрес Bot API (например, тестовый стенд), только `https`, `http` — лишь для loopback. Неверное значение `httpProxy` или `apiBaseUrl` останавливает аккаунт при старте ошибкой с путём опции.
- `send` и `sendAttachment` принимают вложение содержимым: `buffer` (base64 или data URL) с `filename` и `contentType`, в том числе в `attachments[]`; `mediaMaxMb` проверяется до декодирования. Если заданы и путь, и `buffer`, используется путь.
- Голосовые ответы. Канал объявляет ядру `capabilities.tts.voice` (`audio-file`; `mp3`, `m4a`, `wav`, `ogg`, `opus`). Ответ с `audioAsVoice` (директива `[[audio_as_voice]]`, `asVoice` у `send` и `sendAttachment`) уходит вложением MAX `audio` — отдельного типа «голосовое» в Bot API нет. Текст ответа доставляется один раз; если MAX отверг аудио (загрузка или `400`), те же байты уходят файлом.
- SecretRef ядра для `botToken`, `webhookSecret` и `httpProxy` (канал и `accounts.<id>`): контракт секретов канала (`dist/secret-contract-api.js`) виден `openclaw secrets configure/apply/audit`; gateway разрешает ссылки до старта аккаунта, аккаунт с неразрешённой ссылкой не стартует (ошибка с путём опции, без значения и без отката на другие источники), остальные работают. `tokenFile`, `webhookSecretFile` и `MAX_BOT_TOKEN` — как раньше.
- Read-only диагностика аккаунта (`config.inspectAccount`): статус показывает `tokenSource`, `tokenStatus` (`available` / `configured_unavailable` / `missing`) и `mode` (`polling` / `webhook`) без токена и побочных эффектов; аккаунт без токена получает причину с путём опции.
- Статус хода — штатная настройка ядра `streaming.mode: "progress"` (канал и `accounts.<id>`, параметры `streaming.progress.*`): одно сообщение, которое правится по ходу работы агента не чаще раза в секунду и удаляется после доставки ответа. По умолчанию выключено; ошибки статуса не влияют на ход.
- Меню команд кнопками: команда без аргумента, для которой ядро описывает варианты (`/think`, `/fast`, `/reasoning`, `/verbose`, `/usage`, `/elevated`, `/trace`, `/activation`, `/send`, `/tts`, `/session`, `/subagents`, `/acp`, `/tools`), отвечает кнопками, текущий вариант отмечен ✓. Нажатие применяет команду так же, как ввод текстом. Меню и нажатия — только для отправителя с правом на команды.
- Упоминание в группах по шаблонам ядра (`messages.groupChat.mentionPatterns`, `groupChat.mentionPatterns` агента) — только явно заданным; шаблоны, которые ядро выводит из имени агента, в MAX не применяются. Опция `mentionPatterns` (`mode: allow|deny`, `allowIn`, `denyIn`) ограничивает группы, где шаблоны действуют.
- Голосовое без подписи в группе с `requireMention` проверяется на упоминание по транскрипту MAX, а без него распознаётся один раз штатным preflight ядра (только в допущенной группе и от допущенного отправителя); опция группы `groups.<id>.disableAudioPreflight` отключает проверку.
- Долговечная очередь webhook: событие записывается в `<stateDir>/max/inbox-<account>/` до ответа `200`; после рестарта или падения необработанное ставится первым, порядок внутри чата прежний. Ключи обработанных событий (24 ч, до 5000) отсекают повторы MAX и после рестарта. Опция `webhookQueue`: `mode` (`durable` по умолчанию или `memory`), `maxPending` (5000), `overflow` (`reject` по умолчанию — ответ `503`, MAX повторит; `drop` — как в 0.7). Штатная очередь SDK внешним плагинам в OpenClaw 2026.9.x недоступна, поэтому журнал свой, по тому же контракту.
- Опция `maxEventAgeMinutes` (по умолчанию 60, `0` — без ограничения): сообщения, правки, нажатия кнопок и `bot_started` старше этого времени по часам MAX пропускаются с предупреждением в логе. Действует на webhook, восстановленную очередь и long polling.
- Опция `logMessagePreview` (по умолчанию `false`): превью текста (50 символов) в debug-логах для отладки.
- Предупреждение при старте именованного аккаунта, который унаследовал открытую политику (`dmPolicy` или `groupPolicy` = `"open"`), с путём опции, которую стоит задать.
- Ключи схемы, которые 0.7 принимал, но не читал, теперь действуют: `groups.<id>.enabled: false` отключает группу при любой `groupPolicy`, `groups.<id>.systemPrompt` добавляется к системному промпту хода в группе, `groups.<id>.skills` ограничивает навыки хода (`[]` — без навыков); `actions.<действие>: false` скрывает действие инструмента `message` и отклоняет его вызов; `textChunkLimit` задаёт размер части исходящего текста (не больше 4000).

### Changed

- Карточка пакета: иконка `assets/icon.png` (исходник `assets/icon.svg`), подписи и пояснения всех опций канала, `accounts.*` и `groups.*` в `uiHints` манифеста с пометками чувствительных и расширенных опций, описание с перечнем возможностей, ключевые слова и автор в `package.json`.
- Единое наследование: именованный аккаунт (`accounts.<id>`) берёт с уровня канала каждую опцию, которую не задал сам, включая политики доступа и списки; явное значение аккаунта сильнее, списки и `groups` заменяются целиком (штатный `mergeAccountConfig`). Не наследуются опции одного бота: `botToken`, `tokenFile`, `name`, `transport`, `webhookUrl`, `webhookSecret`, `webhookSecretFile`, `webhookPath`. `channels.max.enabled: false` выключает и именованные аккаунты.
- Из JSON- и zod-схемы убраны `default`: gateway записывал умолчания схемы в `accounts.<id>`, и они перекрывали значение канала. Умолчания применяются в коде и не изменились; `channels.defaults.groupPolicy` ядра учитывается, если `groupPolicy` не задан ни у аккаунта, ни у канала.
- Индикатор набора держится весь ход (продление каждые 4 с штатным `createTypingCallbacks`, остановка ядром при завершении, ошибке и отмене) и подчиняется `typingMode` ядра: `typingMode: "never"` выключает его.
- Long polling: пауза после ошибки растёт экспоненциально от 2 до 60 с с jitter и сбрасывается после успеха; `Retry-After` соблюдается; при `401` — повтор раз в 5 минут; остановка аккаунта прерывает паузу сразу.
- Входящее голосовое передаётся ядру фактом `media` с `kind: "audio"` для штатного распознавания (`tools.media.audio`); транскрипт MAX в приоритете и помечает факт `transcribed`. Голосовое, которое не скачалось и не имеет транскрипта, агент видит пометкой `[Voice message: audio unavailable, no transcript]` вместо подписанной ссылки.
- Подсказки агенту для инструмента `message` описывают `asVoice`, `buffer`, `silent`, корни локальных файлов и `actionScope`.
- Диагностика `[MAX API] …` и `[MAX] …` пишется через логгер плагина рантайма, а не в `console` (до инициализации рантайма — по-прежнему в консоль).
- Пакет не включает `scripts/` (служебные скрипты разработки); сборка и установка от них не зависят.
- `README.md` — на русском, английская версия — `README.en.md` (в 0.7 было наоборот: `README.md` на английском, `README.ru.md` на русском); ссылка на другую версию — в начале каждого файла.

### Fixed

- `ReplyToId` ответа не передавался ядру: читался несуществующий `link.message.body.mid`.
- Ошибки доставки ответа агента больше не глотаются: по контракту SDK — `PlatformMessageNotDispatchedError`, если не ушло ничего, и `createChannelPartialDeliveryError`, если часть видна. После сбоя куска текста следующие куски не отправляются.
- Отказ MAX на разметку (`400`) не теряет ответ: сообщение, правка или ответ на нажатие кнопки один раз повторяются обычным текстом.
- `streamMode: "partial"`: финал длиннее 4000 символов больше не обрезается (первый кусок — в черновик, остальные — новыми сообщениями, кнопки на последнем); при отказе правки черновик удаляется, ответ уходит новыми сообщениями.
- Индикатор набора гас на долгих ходах: отправлялся один раз.
- Long polling после рестарта посреди пакета повторял агенту уже обработанные события: ключи обработанных теперь хранятся в журнале аккаунта. Ключ записывается в момент, когда ядро приняло ход (как у webhook), — падение посреди хода больше не даёт двух ходов: возобновлённого ядром и повтора из пакета.
- `channels.max.streaming` не действовал у аккаунта верхнего уровня.
- Ответ агента на нажатие кнопки терял медиа (картинки, файлы, голосовое TTS): текст и клавиатура отвечают на нажатие (`POST /answers`), медиа уходят в чат следом.
- `groupAllowFrom` и `groups.<id>.allowFrom` были объявлены в схеме, но к сообщениям групп не применялись (см. Security).
- При `textChunkLimit` больше 4000 ядро делило текст инструмента `message` на части этого размера, и MAX отклонял сообщение: размер части теперь не превышает 4000.
- Ответ из нескольких частей терял все части, кроме последней: в `streamMode: "partial"` каждая следующая финальная часть заново правила черновик, а в ответе на нажатие кнопки каждая часть (и каждый блок при `streamMode: "block"`) заново отвечала на нажатие, заменяя предыдущую. Теперь черновик и ответ на нажатие получает только первая часть, остальные уходят новыми сообщениями.
- `streamMode: "partial"`: в чате оставался лишний черновик с обрывком ответа, если финал или отложенное обновление приходили, пока первая отправка черновика ещё шла (финал уходил отдельным сообщением, черновик так и висел). Отправки и правки черновика теперь идут по одной, финал ждёт отправку в полёте. Выводы инструментов (`kind: "tool"`) посреди хода уходят отдельными сообщениями и больше не останавливают черновик.
- Два служебных события без сообщения (`bot_started`, `bot_added`, `bot_removed`, `dialog_*`, `chat_title_changed`) от разных пользователей или чатов с одинаковой миллисекундой получали один ключ дедупликации, и второе отбрасывалось как повтор. В ключ добавлены чат и пользователь.
- `streamMode: "partial"`: черновик с обрывком ответа оставался в чате, если ход закончился без финала (`NO_REPLY`, отмена хода, ответ через инструмент `message`). Теперь такой черновик удаляется, как статус хода в режиме `progress`; после ошибки обработки он остаётся как след хода.

### Security

- Локальные файлы исходящих отправок читаются только загрузчиком SDK внутри корней, которые передаёт ядро (media-каталоги gateway, рабочий каталог агента и то, что разрешает политика файловой системы ядра); выход через `..` и symlink закрыт. Действует для `send`, `sendAttachment` (каждого элемента `attachments[]`), адаптера исходящих и ответа агента. Раньше `uploadMedia` читал любой путь. Файл вне корней — ошибка `Local media path is not under an allowed directory`.
- Действия инструмента `message` ограничены чатами, которые допускает политика входящих (`actionScope: "admitted"`): текущий чат хода, запрос владельца или чат, допущенный `dmPolicy`/`allowFrom`/pairing и `groupPolicy`/`groups`/списками отправителей. Раньше отправка, правка, удаление и закрепление выполнялись в любом чате бота, и инъекция в одном чате могла править или удалять сообщения в другом. Отказ — ошибка инструмента до изменения в MAX; если чат определить не удалось — тоже отказ. Без ограничений действуют только вызовы, которые ядро помечает `senderIsOwner: true`: ход владельца, `openclaw message` из CLI, чат администратора в Control UI, RPC `message.action` клиента с правами администратора и `senderIsOwner: true`.
- Вызов без признака владельца или с `senderIsOwner: false` — heartbeat, субагенты, запуски по расписанию без авторитета сообщений, запуски плагинами и хуками — больше не считается вызовом оператора: его действия `message` ограничены допущенными чатами, а в группе со списком отправителей получают отказ (автора запроса нет). Доставки ядра — ответы агента, напоминания, объявления автоматизаций — идут через адаптер исходящих, а не через действия инструмента, и не затронуты.
- Вне чата текущего хода `edit` и `delete` работают только с сообщениями, которые отправил сам бот; автор берётся из того же запроса `GET /messages/{mid}`, которым определяется чат, id бота — из пробы `GET /me` при старте аккаунта (если её не было — один запрос, затем из памяти). Раньше в допущенном чате проверялся только чат, и инъекция могла удалить чужое сообщение в допущенной группе, где бот администратор. В чате текущего хода и для владельца — как раньше.
- `send`, `sendAttachment` и `sticker` с `replyTo` (и `send` с `presentation`) при активном `actionScope` отвечают только на сообщение чата, в который уходят: чат сообщения-адресата сверяется запросом `GET /messages/{mid}` — только когда `replyTo` задан; для сообщения, с которого начался ход, в его чате запроса нет. Ответ на сообщение другого чата или неизвестного — отказ до отправки. Раньше цитата ответа могла показать в целевом чате текст сообщения из другого чата. Для владельца и при `actionScope: "off"` — как раньше.
- «Текущий чат» хода засчитывается только аккаунту, через который пришёл ход: действие `message` другого бота в той же группе проверяется по его собственной политике.
- `send` с `presentation` (карточка, кнопки) тоже проходит `actionScope` и `actions.send`: такую отправку ядро доставляет само через адаптер исходящих, минуя `handleAction`, поэтому проверка выполняется в `prepareSendPayload` до доставки. Раньше `send` с `presentation` уходил в любой чат бота без проверки.
- Списки отправителей в группах применяются: `groups.<id>.allowFrom`, иначе `groupAllowFrom` — к сообщениям, нажатиям кнопок, командам, голосовому preflight и скоупингу действий; вложения недопущенного отправителя не скачиваются. `allowFrom` личных сообщений на группы не переносится.
- Ответ на вопрос `ask_user` кнопкой по `allowFrom: ["*"]` в группе требует, чтобы группа была допущена и нажавший был в её списке отправителей; раньше такой ответ мог дать любой участник любой группы, где видна клавиатура. Явно перечисленные в `allowFrom` отвечают, как раньше.
- Текст сообщений, подписи и транскрипты не пишутся в логи; раньше в debug-лог попадало превью входящего (50 символов) и полный текст правки.
- Ссылка на медиа со схемой в любом регистре (`HTTP://`, `Https://`) скачивается через прокси аккаунта; раньше такая ссылка уходила в загрузчик локальных файлов ядра, который скачивал её сам, напрямую, мимо `httpProxy`.
- Картинка передаётся в MAX ссылкой только для публичного https-хоста; прочие удалённые медиа скачиваются SSRF-защищённым загрузчиком ядра в память, без временного файла.

### Изменения поведения при обновлении с 0.7

| Что меняется | Как вернуть поведение 0.7 |
|---|---|
| В ходе не владельца инструмент `message` действует только в текущем чате и в чатах, которые допускает политика входящих | `actionScope: "off"` (строже — `"current"`) |
| Вызов без `senderIsOwner: true` (heartbeat, субагент, запуск по расписанию без авторитета сообщений) ограничен допущенными чатами; в группе со списком отправителей — отказ | `actionScope: "off"` |
| Вне чата текущего хода `edit` и `delete` не трогают чужие сообщения — только сообщения бота | `actionScope: "off"` |
| `replyTo` отправки должен указывать на сообщение того же чата, куда она уходит; иначе отказ | `actionScope: "off"` |
| Локальные файлы отправляются только из разрешённых каталогов | Отключения нет: скопировать файл в рабочий каталог агента |

## 0.7.1 - 2026-09-26

### Fixed

- Webhook-режим больше не глохнет с `GatewayDrainingError: Gateway is draining; new tasks are not accepted`. Gateway выдаёт обработчику HTTP-роута допуск работы (root-work admission в `AsyncLocalStorage`) только на время запроса и освобождает его в `finally` после ответа; обработка апдейта, запущенная после ответа `200` из того же async-контекста, наследовала освобождённый допуск, и запуск агента/сессии отвергался как «draining», хотя gateway работал. Теперь обработчик роута после проверки секрета, тела и дубликата только кладёт апдейт в очередь аккаунта (`webhook-queue.ts`), а задача аккаунта — она стартует вне любого запроса, как цикл polling, — забирает апдейты и вызывает `dispatchUpdate` в своём контексте: внутри чата строго по порядку, между чатами параллельно, не больше 4. Ошибки обработки логируются, цикл не падает. При остановке аккаунта начатые апдейты дорабатывают (ожидание до 3 с), принятые, но не начатые передаются следующему старту того же аккаунта в процессе (MAX их не повторит); очередь ограничена 5000 апдейтами. Тесты: `AsyncLocalStorage`-модель допуска (dispatch идёт в контексте задачи аккаунта, а не запроса, в том числе сквозь `handleMaxWebhookRequest`), порядок в чате, лимит параллельности, abort и передача остатка.
- Цели `user:<id>` (и `max:user:<id>`) проходят нормализацию справочника канала: раньше `normalizeTarget`/`looksLikeId` принимали только числа, `message` с `target: "user:12345678"` доходил до плагина как `12345678` → `chat_id` → `dialog.not.found`. Кроме того, если голое положительное число как `chat_id` получает `dialog.not.found`/`chat.not.found`, отправка один раз повторяется как `user_id` (первая попытка не доставлена, дубля нет).
- Инструмент `message`: `send` и `sendAttachment` с несколькими `attachments[]` отправляют все вложения через `sendMaxMediaGroup` (изображения/видео альбомами до 12, аудио и файлы по одному, порядок сохраняется, подпись на первом сообщении) и возвращают `messageIds`; раньше уходило только первое вложение. Частичный сбой не теряет уже отправленное: ошибки — в `mediaErrors`, исключение — только если не ушло ничего.
- Закрепление в диалогах: MAX отвечает на `PUT /chats/{id}/pin` в диалоге `400 proto.payload "Method is not available for dialogs"`. `pinMaxMessage` теперь не вызывает API для диалогов (цель `user:<id>`, `chat_type: "dialog"` у отправленного сообщения или `GET /chats/{id}` для положительного id) и возвращает `pinned: false` с причиной; `pinDeliveredMessage` и ответы агента с `delivery.pin` в диалоге больше не пишут ERROR, действие `pin` и `send` с `pin` возвращают `pinned: false` (`reason`/`pinSkipped`). Заменяет поведение 0.7.0 «chat id диалога из `GET /messages/{mid}`».

## 0.7.0 - 2026-09-26

### Added

- `capabilities.unsend` и `capabilities.reply` (`DELETE /messages` и ответы через `link.type=reply` уже поддерживались, но не объявлялись).
- Webhook-ingress на HTTP-сервере gateway: роут регистрируется из жизненного цикла аккаунта через `registerPluginHttpRoute` (`plugin-sdk/webhook-ingress`: `auth: "plugin"`, `match: "exact"`, `pluginId`/`source`, `replaceExisting`, `throwOnFailure`) и обслуживается `handleMaxWebhookRequest`. Путь — `webhookPath`, иначе pathname `webhookUrl`, иначе `/max/webhook` (раньше `/max`). Секрет `X-Max-Bot-Api-Secret` сверяется timing-safe до чтения тела (401), тело без `update_type` — 400, валидное обновление получает 200 сразу, обработка идёт асинхронно с логированием ошибок (раньше ответ ждал `onUpdate` и при ошибке отдавал 500, провоцируя повторы MAX). Повторные доставки отсекаются LRU на 1000 ключей `(update_type, timestamp, mid|callback_id)`. Тесты: регистрация роута с mock, 200/400/401/405, дедупликация, сквозной прогон через настоящий `node:http` и `fetch`.
- Режимы транспорта `transport: "polling" | "webhook"` (по умолчанию `webhook`, если задан `webhookUrl`, иначе `polling`). В webhook-режиме polling не запускается: после регистрации роута плагин делает `GET /subscriptions`, удаляет подписки этого бота на другие URL и вызывает `POST /subscriptions {url, update_types, secret}`; при остановке подписка сохраняется, чтобы рестарт не терял события (снимается переходом на `polling` или вручную `DELETE /subscriptions?url=`). В polling-режиме активная подписка (при ней MAX не отдаёт `GET /updates`) удаляется с предупреждением. Статус webhook-аккаунта публикуется без `lastTransportActivityAt`, как у Telegram webhook, чтобы тихий канал не считался stale-socket. Секрет: `webhookSecret`, новый `webhookSecretFile` (обычный файл, не symlink) или сгенерированный один раз и сохранённый в state-файле аккаунта; формат проверяется по схеме MAX (5–256 символов `[A-Za-z0-9_-]`). Схема конфига и `openclaw.plugin.json`: `transport`, `webhookSecretFile`, `transport="webhook"` требует `webhookUrl`; тест сверяет поля манифеста с zod-схемой.
- README: раздел «Webhook» — требования MAX (HTTPS:443, 200 за 30 с, до 10 повторов, автоотписка через 8 часов, секрет в заголовке, при подписке не работает long polling), устройство роута и подписки, пример конфига (`https://bot.example.com/max/webhook`, секрет файлом), порядок включения (сначала деплой и рестарт с новым кодом в polling-режиме) и откат; обновлены таблица полей и SKILL.md.
- Контракт `presentation` в исходящем пути: адаптер объявляет `presentationCapabilities` (кнопки, select, context, divider, таблицы и графики; лимиты MAX: текст кнопки ≤128, payload ≤1024 байт, ≤30 рядов, ≤210 кнопок, текст ≤4000) и `renderPresentation`: title/tone → жирный заголовок с эмодзи тона, text/context/divider → MAX markdown, table/chart → моноширинный блок, `buttons` → `inline_keyboard` по 3 в ряд (url и web-app с URL → `link`; command/callback/approval/question → `callback` с приватным payload), `select` → ряды callback-кнопок по 2; неотрисованные кнопки остаются подписями в тексте. `sendPayload` режет текст длиннее 4000 символов (клавиатура на последнем куске) и сам рендерит payload, если presentation дошла до него неотрисованной; ответы агента (`deliverMaxReply`) проходят ту же политику через `renderPresentationForDelivery`. `delivery.pin`: `deliveryCapabilities.pin` + `pinDeliveredMessage` → `PUT /chats/{chatId}/pin` c проверкой `assertDirectAdapterHandoff` перед каждым запросом; для `user:<id>` chat id диалога берётся из `GET /messages/{mid}`. Ответ агента с `delivery.pin` закрепляет первое доставленное сообщение.
- Обратный путь presentation-кнопок на `message_callback`: approval → `resolveApprovalOverGateway` с явным `approvalKind` (`plugin-sdk/approval-gateway-runtime`), вариант `ask_user` → `questionGatewayRuntime.resolveOption` (`plugin-sdk/question-gateway-runtime`), итог — всплывающее уведомление через `POST /answers`. Нажимать approval могут только отправители, явно перечисленные в `allowFrom` (для вопросов достаточно `*`). Command-кнопка возвращается текстом команды и идёт штатным путём нативных команд; непрозрачный callback приходит агенту как `callback_data: <value>` и не разбирается как slash-команда. Payload обычных `channelData.max.buttons` по-прежнему приходит текстом без изменений. Тесты round-trip: рендер → нажатие в форме живой фикстуры → `dispatchUpdate`.
- Расшифровка голосовых от MAX: если у аудио-вложения есть `transcription` (сосед `payload` в `AudioAttachment`), агент получает `[Voice transcript: …]` в тексте, а медиа-факт помечается `transcribed: true` (`ChannelInboundMediaInput`), чтобы ядро не запускало STT повторно. Файл по-прежнему скачивается; без расшифровки (`null`, пусто) — прежний путь через STT ядра.
- Webhook-режим сверяет подписку раз в 12 минут (`GET /subscriptions`): если MAX снял её после 8 часов недоставки, плагин пересоздаёт `POST /subscriptions` с тем же секретом и списком событий и пишет warning; сетевые ошибки проверки только логируются, проверка не запускается внахлёст, таймер снимается при остановке аккаунта. Раньше после такой отписки события не приходили до рестарта gateway.
- Альбомы и картинки по ссылке. `sendMaxMediaGroup` отправляет несколько медиа минимумом сообщений: подряд идущие изображения и видео — одним сообщением до 12 штук (лимит docs «Медиафайлы»), аудио и файлы — по одному (MAX не сочетает файл с фото/видео); порядок сохраняется, подпись и reply — на первом сообщении, клавиатура — на последнем. Используется в ответах агента (`deliverMaxReply`, раньше каждая картинка — отдельное сообщение) и в `outbound.sendPayload` (раньше из `mediaUrls` отправлялся только первый элемент). https-ссылки на изображения уходят как `image.payload.url` без скачивания и загрузки; если MAX отвергает сообщение (`MaxApiError`), ссылки скачиваются, загружаются через `POST /uploads` и сообщение отправляется ещё раз. Прочие удалённые URL (http/https, не картинки) скачиваются во временный файл и загружаются — раньше `sendMaxMediaMessage`/`sendMedia` пытались прочитать URL как локальный путь. `sendMaxMediaMessage` сохранил сигнатуру, добавлена опция `mediaMaxBytes` (из `mediaMaxMb` аккаунта).
- Точка входа для setup-режима `setup-entry.ts` (`defineSetupPluginEntry`, `openclaw.setupEntry: ./dist/setup-entry.js`): OpenClaw грузит её вместо полной, когда канал выключен или не настроен.

### Fixed

- Совместимость с OpenClaw 2026.9.3: конфиг читается через `config.current()` / `replaceConfigFile` (в рантайме плагинов убраны `loadConfig`/`writeConfigFile`), с откатом на старый API. Раньше исходящая отправка через `outbound.sendText/sendPayload` падала с `config.loadConfig is not a function`.
- Тесты на OpenClaw 2026.9.6 снова зелёные. `dmPolicy`/`groupPolicy` с дефолтами строятся на zod самого плагина: обёртка `.optional().default()` над enum-ами SDK ломалась («expected nonoptional»), когда плагин и gateway подтягивали разные копии zod (4.4 в каталоге плагина против 4.6 у gateway); значения сверяются с SDK тестом. Заглушка `IncomingMessage` в webhook-тестах получила `socket`, как у настоящего запроса.
- Команды бота регистрируются через `PATCH /me/commands` с телом `{commands:[…]}`: прежний `PATCH /me` MAX отвечает 404 `method.not.found`, так что `channels.max.commands` фактически не применялись. Удалены `MaxBotPatch` и `editMyInfo`; `setMyCommands` возвращает `BotCommandsInfo`.
- `message_callback`: плагин брал `callback.message`, которого в API нет (`message` — сосед `callback` в апдейте), поэтому ответ на нажатие кнопки уходил в `{chat_id: user_id}` вместо реального чата диалога/группы. Теперь recipient берётся из `update.message.recipient`, откат на пользователя — только если сообщение с клавиатурой удалено (`message: null`); `user_locale` пробрасывается. Нажатие кнопки бота в группе считается обращением к боту и не отсекается требованием упоминания. Типы `MessageCallbackUpdate`/`MaxCallback` приведены к схеме; тесты на живой фикстуре (DM) и групповой recipient.
- Цели `@username` и ссылки max.ru больше не резолвятся через `GET /chats/{link}`: такого варианта нет в схеме, живой вызов отвечает `chat.not.found`. `resolveMaxTarget` сразу бросает понятную ошибку («MAX API does not resolve @username … use a numeric chat_id … or user:<id>») без запроса к API; `MaxApi.getChat` принимает только числовой id. SKILL.md обновлён.
- Edit-стриминг (`streamMode: "partial"`) больше не теряет кнопки финального ответа: `editMaxMessage` принимает `buttons` и передаёт `inline_keyboard` в `attachments` `PUT /messages` (без кнопок поле не отправляется — по схеме `null`/отсутствие сохраняет текущие вложения, пустой список их удаляет). Финальная правка черновика делается и при неизменном тексте, если есть кнопки; медиа финального ответа уходят без повторной клавиатуры.
- Временные файлы медиа: имя скачанного файла больше не подставляется в путь как есть (`/tmp/max-media-<ts>-${fileName}` позволял `../` и разделители из имени, пришедшего от удалённого сервера). Новая `withRemoteMediaTempFile` (`src/media-temp.ts`) — единая функция «скачать во временный файл»: загрузка через `fetchRemoteMedia` с лимитом `mediaMaxMb`, приватный каталог `mkdtemp`, файл `0600`, удаление каталога в `finally`; её используют ответы агента и действие `send`. `sanitizeMaxFileName` оставляет один сегмент пути без `..`, управляющих и зарезервированных символов, ограничивает длину 120 символами с сохранением расширения и добавляет расширение по `contentType`; им же чистится имя входящего вложения, которое уходит агенту и в `saveMediaBuffer`. Тесты на опасные имена и очистку при ошибке.
- Входящие вложения скачиваются только после проверок DM (allowlist/pairing) и групп (allowlist, упоминание): медиа из игнорируемых сообщений больше не тратят трафик и место на диске, `getVideoInfo` для них не вызывается. Тесты на группу вне allowlist, сообщение без упоминания и DM от чужого отправителя.
