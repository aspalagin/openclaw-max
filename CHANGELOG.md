# Changelog

All notable changes to this project are documented in this file.

## Unreleased (0.8.0)

### Added

- Опция `actionScope` (`channels.max.actionScope` и `accounts.<id>.actionScope`): в каких чатах инструмент `message` может выполнять `send`, `sendAttachment`, `sticker`, `edit`, `delete`, `pin`, `unpin`. `admitted` (по умолчанию) — текущий чат хода, запрос владельца (`senderIsOwner`) или чат, который допускает политика входящих (`dmPolicy` с `allowFrom` и хранилищем pairing, `groupPolicy` с `groups`); `current` — ход не владельца действует только в своём чате; `off` — без проверки плагина (поведение 0.7.x).

- Пересланные сообщения доходят до агента. Содержимое пересылки берётся из `link.message` (по схеме MAX это `MessageBody`), включая чистую пересылку с `body = null`: агент получает блок `[Forwarded message from <автор>]` с текстом и описаниями вложений, а автор и тип источника (`user` или `channel`) уходят в штатные поля SDK (`SupplementalContext.forwarded` → `ForwardedFrom*`). Собственный комментарий отправителя идёт первым, пересылка — после него. Вложения пересылки скачиваются только после проверок DM и групп, с теми же лимитами. Пересланный текст не разбирается как команда или inline-директива (`CommandBody` — только собственный текст). У сообщения без `body` нет своего `mid`: для дедупликации используется стабильный синтетический id, ответ уходит без `link`; webhook-дедупликация берёт `mid` из `link.message`. Правка без `body` пропускается, а не роняет обработку.
- Ответ на сообщение: `ReplyToId` берётся из `link.message.mid` (раньше читался несуществующий `link.message.body.mid`, и id не передавался). Агент получает цитату исходного сообщения до 1000 символов и её автора через `SupplementalContext.quote` (`ReplyToBody`, `ReplyToSender`); для сообщения без текста — типы вложений.
- Отказ разметки не теряет ответ: если MAX отвечает `400` на форматированный текст (кроме `chat.not.found`/`dialog.not.found`, `attachment.not.ready` и запрета метода в диалоге), сообщение, правка или ответ на нажатие кнопки один раз повторяются без `format`, как написаны; клавиатура сохраняется. Отдельного кода ошибки разметки у MAX нет, а `400` означает, что сообщение не создано, поэтому повтор не дублирует.
- Ошибки доставки ответов агента больше не глотаются (`deliverMaxReply` раньше только писал в лог, и ядро считало ответ доставленным). По контракту SDK: если что-то уже видно (куски текста, альбом, черновик стриминга) — `createChannelPartialDeliveryError` с `messageIds` и видимым текстом; если MAX отверг отправку целиком (`4xx`) — `PlatformMessageNotDispatchedError` (повторяемая только для `429`); `5xx`, таймаут и сетевые ошибки пробрасываются как есть (отправка могла пройти). После сбоя куска текста следующие куски не отправляются (без дыр в ответе), медиа отправляются; ответ на нажатие кнопки при ошибке тоже отклоняется.
- Стриминг правкой (`streamMode: "partial"`): финальный ответ длиннее 4000 символов больше не обрезается — первый кусок правит черновик, остальные уходят новыми сообщениями, кнопки на последнем куске. Если MAX отверг правку черновика, устаревший черновик удаляется, а ответ уходит новыми сообщениями (раньше ошибка глоталась и ответ терялся).

- Индикатор набора держится весь ход агента: `typing_on` продлевается каждые 4 с через штатный жизненный цикл SDK (`createTypingCallbacks`, `dispatcherOptions.typingCallbacks`) и останавливается ядром при завершении, ошибке и отмене хода; страховочный TTL SDK — 60 с без сигналов ядра. Раньше индикатор отправлялся один раз и гас на долгих ходах. Момент старта определяет `typingMode` ядра: в личке и при упоминании сразу, в группе без упоминания — когда модель начинает отвечать; `typingMode: "never"` теперь выключает индикатор. Запрос индикатора — одна попытка с дедлайном 5 с, без повторов (запоздалый индикатор мог бы появиться после ответа); после двух ошибок подряд продление прекращается, ход не прерывается.
- `heartbeat.sendTyping` и `heartbeat.sendTypingGuarded`: индикатор набора перед heartbeat-ходом, на ходах из gateway и при прогрессе фоновых задач в чате MAX; guarded-вариант учитывает отмену хода и перепроверяет право отправки перед запросом (цели `user:<id>` пропускаются — эндпоинт действий принимает только `chat_id`).
- Опции `notify` и `disableLinkPreview` (`channels.max.*` и `accounts.<id>.*`, именованный аккаунт наследует значение канала): умолчания push-уведомлений и превью ссылок для всех отправок — ответов агента (включая черновик стриминга), адаптера исходящих и действий `send`, `sticker`, `sendAttachment` инструмента `message`. Явное значение в вызове сильнее умолчания: флаг `silent` ядра (`silent: false` — явное «с уведомлением»), затем `channelData.max.notify` / `silent` / `disableLinkPreview`. Раньше `silent` ядра игнорировался, а уведомления настраивались только через `channelData`.
- В каналы MAX тихая отправка не уходит: по документации `POST /messages` канал принимает только `notify = true` или без поля, поэтому для `notify: false` в `chat_id` плагин один раз узнаёт тип чата (`GET /chats/{chatId}`, кэш на процесс) и для канала отправляет с уведомлением. Если тип прочитать не удалось (кроме `chat.not.found`), сообщение тоже уходит с уведомлением — доставка важнее тишины.
- Long polling: пауза после ошибки теперь экспоненциальная — 2 с, удвоение до потолка 60 с, jitter до +20 % (`computeBackoff` SDK), сброс после успешного запроса; `Retry-After` сервера соблюдается (не дольше 10 мин); остановка аккаунта прерывает паузу сразу (`sleepWithAbort` SDK). Отказ токена (`401`) повторяется раз в 5 минут с понятной ошибкой в логе, а не каждые 3 секунды. Раньше пауза была фиксированной, 3 с.
- Входящие контакты: агент получает имя и телефоны, разобранные из VCard (`FN`, иначе `N`; `TEL`; переносы строк, экранирование и quoted-printable), и профиль MAX из `max_info` (`user_id`, `@username`), а не сырой `vcf_info`. Геолокация — координаты и ссылка на Яндекс Карты с меткой. Share-карточка — заголовок, описание (до 300 символов, в одну строку) и ссылка, что из этого есть.
- Опция `mediaMaxCount` (канал и аккаунт, по умолчанию 12 — полный альбом MAX): сколько медиавложений (изображения, стикеры, видео, аудио, файлы) скачивается из одного входящего сообщения, включая пересланные; остальные не скачиваются, агент получает пометку `[N more media attachment(s) not loaded: limit of M per message]`, код стикера и транскрипт голосового сохраняются. Лимит размера (`mediaMaxMb`) действует отдельно.

- Опции `httpProxy` и `apiBaseUrl` (канал и аккаунт; именованный аккаунт наследует значение канала). `httpProxy` — HTTP(S)-прокси для всего исходящего трафика плагина к MAX: вызовы Bot API, загрузка файлов на upload-адреса, скачивание входящих вложений и медиа по ссылке (через `fetchRemoteMedia` ядра с `dispatcherPolicy: explicit-proxy`, SSRF-проверки ядра сохраняются). TLS до MAX проверяется внутри туннеля тем же набором CA, включая сертификат Минцифры. Учётные данные из адреса прокси не попадают в логи и ошибки (в логе старта — `http://***@host:port`), поле помечено чувствительным (`registerSensitiveConfigSchema`, `uiHints.sensitive`); `""` у аккаунта отключает унаследованный прокси. Loopback-адреса идут мимо прокси. `apiBaseUrl` — свой адрес Bot API (тестовый стенд), префикс пути сохраняется; только `https`, `http` — лишь для loopback, чтобы токен бота не ушёл открытым текстом. Неверное значение любой из опций останавливает аккаунт при старте понятной ошибкой с путём опции, а все запросы этого аккаунта отказывают без обхода прокси. Штатного публичного механизма прокси для внешних плагинов в SDK нет (`makeProxyFetch` только в устаревшем `infra-runtime` и приватном `fetch-runtime`), поэтому API идёт через собственный `ProxyAgent` undici, а скачивание медиа — через штатный `dispatcherPolicy` ядра.

- `sendAttachment` (и `send`) с содержимым без пути: `buffer` (base64 или data URL `data:<тип>;base64,…`) с `filename` и `contentType` (синонимы `fileName`, `mimeType`) отправляется как вложение, в том числе в элементах `attachments[]`; тип вложения MAX — по расширению имени, при его отсутствии имя дополняется расширением по `contentType` (или типу из data URL). Лимит `mediaMaxMb` проверяется до декодирования, неверный base64 — ошибка до обращения к MAX. Если передан и путь, и `buffer` (ядро заполняет оба), используется путь — через защищённый загрузчик, как раньше. Раньше `buffer` без пути принимался за путь к файлу и отправка падала.

- Входящие голосовые по контракту ядра: аудиовложение MAX передаётся фактом `media` с `kind: "audio"`, поэтому штатное распознавание ядра (`tools.media.audio`) выбирает его даже при общем типе содержимого от CDN MAX. Приоритет у транскрипта MAX (`AudioAttachment.transcription`): текст идёт агенту как `[Voice transcript: …]`, факт помечается `transcribed`, и ядро не распознаёт его повторно; без транскрипта распознаёт ядро, а при его ошибке оставляет свою пометку. Голосовое, которое не удалось скачать и у которого нет транскрипта, агент видит как `[Voice message: audio unavailable, no transcript]` — раньше в текст попадала подписанная ссылка MAX. Сообщение совсем без текста, вложений и пересылки пишется в лог (`Skipping empty message`), чтобы вживую проверить сообщения о пустых голосовых в long polling.

- Голосовые ответы. Канал объявляет ядру `capabilities.tts.voice` (`synthesisTarget: "audio-file"`, форматы `mp3`, `m4a`, `wav`, `ogg`, `opus`): синтез остаётся обычным (MP3 по умолчанию, без перекодирования), а ответ TTS в этих форматах ядро помечает `audioAsVoice`. Голосовой ответ (`audioAsVoice`, директива `[[audio_as_voice]]`, `asVoice`/`audioAsVoice` у `send` и `sendAttachment` инструмента `message`, `audioAsVoice` адаптера исходящих) уходит вложением MAX `audio` — отдельного типа «голосовое» в Bot API нет; при голосовой отправке аудио, распознанное только по MIME (`.oga`, `audio/webm`), тоже идёт как `audio`. Текст ответа доставляется один раз: в ответе агента — отдельным сообщением (или в черновике стриминга), голосовое без подписи, `spokenText` в чат не выводится; если ответ только голосовой, неокончательный черновик стриминга удаляется после доставки аудио. Если MAX отказал в аудио (загрузка или сообщение с кодом 400, в том числе необработанное вложение после повторов), те же байты отправляются один раз файлом; после 5xx и таймаутов повтора нет. Локальный файл аудио читается тем же защищённым загрузчиком, что и прочие медиа.

- Секреты как SecretRef ядра: `botToken`, `webhookSecret` и `httpProxy` (канал и `accounts.<id>`) принимают наряду со строкой ссылку `{ source: "env" | "file" | "exec" | "store", provider, id }`; `tokenFile`, `webhookSecretFile` и `MAX_BOT_TOKEN` работают как раньше. Контракт секретов канала (`dist/secret-contract-api.js` и `ChannelPlugin.secrets`) объявляет эти пути для `openclaw secrets configure/apply/audit` и для разрешения gateway при старте: ссылка разрешается в снимок рантайма до запуска аккаунта, аккаунт с неразрешённой ссылкой изолируется (владелец `max:<accountId>`), остальные аккаунты работают. Неразрешённая ссылка — ошибка при старте аккаунта с путём опции и ссылкой `source:provider:id`, без значения и без отката на `tokenFile`, `MAX_BOT_TOKEN`, прямое соединение или сгенерированный секрет webhook. Манифест описывает поля схемой SecretInput ядра, `uiHints` помечает `botToken` и `webhookSecret` чувствительными. Статус и `describeAccount` показывают `tokenStatus` (`available` / `configured_unavailable` / `missing`).

- Диагностика аккаунта без раскрытия секретов: штатный `config.inspectAccount` для read-only статуса (`openclaw status`, `channels status`, doctor) — `enabled`, `configured`, `tokenSource` (`config` / `file` / `env` / `none`), `tokenStatus` (`available` / `configured_unavailable` / `missing`), `mode` (`polling` / `webhook`), без токена и без побочных эффектов. SecretRef, недоступный в текущей команде, показывается как «настроен, но недоступен», а не «не настроен». Аккаунт без токена получает `stateReason` с путём опции (`channels.max.tokenFile is missing, empty or not a regular file`, `no bot token: set …`) — в статусе и в сообщении проблемы; путь самого файла не выводится.

- Статус хода (`streaming.mode: "progress"` — штатная настройка ядра, канал и `accounts.<id>`): пока агент работает, в чате одно сообщение, которое правится по ходу — штатный компоновщик ядра (`createChannelProgressDraftCompositor`: заголовок статуса, план, запросы подтверждения; строки инструментов — с `streaming.progress.toolProgress: true`; `label`, `labels`, `maxLines`, `maxLineChars`, `commandText` — штатные). Сообщение появляется после штатной задержки 1,5 с (на быстрых ходах его нет), без push-уведомления и разметки, правится не чаще раза в секунду (`createDraftStreamLoop`; лимит MAX — две правки в секунду на чат) и удаляется после доставки ответа (`createLivePreviewLifecycle`); ход без ответа (NO_REPLY, ответ инструментом `message`) тоже убирает его. После ответа-ошибки или неудачной доставки статус остаётся как след хода — как у Discord. Ошибка отправки или правки статуса останавливает только статус: ход и ответ не страдают. При включённом `/verbose` статус уступает штатным сообщениям прогресса. `streaming.mode` имеет приоритет над `streamMode` (`partial` и `block` работают как раньше); по умолчанию выключено.

- Меню команд кнопками. Команда без аргумента, для которой ядро описывает меню вариантов (`argsMenu`: `/think`, `/fast`, `/reasoning`, `/verbose`, `/usage`, `/elevated`, `/trace`, `/activation`, `/send`, `/tts`, `/session`, `/subagents`, `/acp`, `/tools`), открывает варианты кнопками — штатные `resolveCommandArgMenu`, `formatCommandArgMenuTitle`, `buildCommandTextFromArgs` из `plugin-sdk/command-auth-native`; варианты `/think` и `/fast` учитывают модель сессии. Нажатие отправляет в ядро текст выбранной команды (`/think high`) и применяется так же, как ввод текстом. Текущий вариант отмечен ✓ по записи сессии (`runtime.agent.session.getSessionEntry`), для `/fast` — по штатному `resolveFastModeState`. Меню видит только отправитель с правом на команды (штатный `resolveCommandAuthorization`, как ядро решает для текстовой команды); нажатие проходит политику DM и групп, право на команды и проверку, что ядро ещё предлагает этот вариант, — иначе всплывающее уведомление вместо применения. Плагин не читает базы и не пишет в конфиг; список команд бота в MAX по-прежнему только из `channels.max.commands`.

- Упоминание в группах по шаблонам ядра: `messages.groupChat.mentionPatterns` и `groupChat.mentionPatterns` агента (штатные `buildMentionRegexes`, `matchesMentionPatterns`). Прежние способы — `@username`, разметка `user_mention`, ответ на сообщение бота — работают как раньше. Шаблоны действуют, только если заданы явно: шаблоны, которые ядро само выводит из имени и эмодзи агента (`identity`), в MAX не применяются, чтобы бот не начал отзываться в группах на имя без настройки. Новая опция `mentionPatterns` (канал и `accounts.<id>`; штатная политика ядра `mode: allow|deny`, `allowIn`, `denyIn` по id группы) ограничивает группы, где шаблоны действуют.
- Голосовое без подписи в группе с `requireMention`: если заданы шаблоны, упоминание ищется в распознанном тексте. Сначала — в транскрипте MAX (без скачивания); иначе голосовое скачивается с лимитами `mediaMaxMb` и `mediaMaxCount` и распознаётся один раз штатным preflight ядра (`createChannelPreflightAudio` из `plugin-sdk/media-understanding-runtime`, `tools.media.audio`). Распознавание — только в группе, прошедшей политику групп, и для отправителя из `groups.<id>.allowFrom` или `groupAllowFrom`, если списки заданы. Распознанный текст уходит агенту в штатном формате (`formatAudioTranscriptForAgent`), факт медиа помечен `transcribed`, поэтому конвейер ядра не распознаёт его второй раз; штатное эхо транскрипта (`echoTranscript`) отправляется после прохождения фильтра. Ошибка скачивания или распознавания означает «упоминания нет». Новая опция группы `groups.<id>.disableAudioPreflight` отключает проверку голосовых.
- Долговечная очередь webhook: принятое обновление записывается в журнал аккаунта до ответа `200` (`<stateDir>/max/inbox-<account>/`, файл на событие `0600`, каталог `0700`, запись штатным `writeJsonFileAtomically`), поэтому рестарт или падение gateway его не теряют: старт аккаунта ставит необработанные записи прошлого процесса первыми, порядок внутри чата и параллельность между чатами прежние. Запись завершается, как только ядро приняло ход агента (публичная опция ответа `turnAdoptionLifecycle.onAdopted`: дальше прерванный ход возобновляет само ядро), иначе — по окончании обработки; падение до принятия хода (проверки, скачивание вложений) — событие обрабатывается снова после старта. Обработанное событие удаляется, его ключ (`update_type:timestamp:mid`) 24 ч отклоняет повтор MAX и после рестарта (до 5000 ключей). Не удалось записать или очередь полна — ответ `503`, MAX повторит доставку. Повреждённая запись пропускается с предупреждением, повреждённый `completed.json` — пустой набор ключей; содержимое сообщений в лог не попадает. Каталог состояния недоступен на запись — прежняя очередь в памяти и предупреждение при старте. Штатная очередь SDK (`createChannelIngressMonitor` над `runtime.state.openChannelIngressQueue`) в этой версии OpenClaw доступна только встроенным и официальным плагинам из каталога ядра, поэтому журнал свой, по тому же контракту.
- Long polling не повторяет обработанное после рестарта: marker сохраняется только после всего пакета, поэтому рестарт посреди пакета снова получает его целиком (потерь нет), а дедупликация ядра по `MessageSid` живёт только в памяти процесса — уже обработанные события пакета уходили агенту второй раз. Теперь ключ каждого обработанного события записывается в тот же журнал аккаунта (`completed.json`), и повтор пропускается. При переходе с webhook на polling необработанные события из журнала обрабатываются первыми. Журнал недоступен — polling работает как раньше, с предупреждением.
- Опция `webhookQueue` (канал и `accounts.<id>`): `mode` — `durable` (по умолчанию) или `memory` (очередь 0.7); `maxPending` — предел принятых, но не обработанных событий (по умолчанию 5000); `overflow` — `reject` (по умолчанию, ответ `503` и повтор от MAX) или `drop` (ответ `200` и отбрасывание, как в 0.7).
- Опция `maxEventAgeMinutes` (канал и `accounts.<id>`, по умолчанию 60, `0` — без ограничения): сообщения, правки, нажатия кнопок и `bot_started` старше этого времени по часам MAX пропускаются с предупреждением в логе вместо ответа — после долгого простоя бот не отвечает на сообщения многочасовой давности. Действует на webhook, на восстановленную после рестарта очередь и на long polling; события реестра чатов (`bot_added`, `bot_removed`, `chat_title_changed` и др.) обрабатываются всегда.

### Changed

- Единое наследование: именованный аккаунт (`accounts.<id>`) берёт с уровня канала каждую опцию, которую не задал сам (`dmPolicy`, `allowFrom`, `groupPolicy`, `groupAllowFrom`, `groups`, `mediaMaxMb`, `mediaMaxCount`, `markSeen`, `streamMode`, `actionScope`, `notify`, `disableLinkPreview` и др.); явное значение аккаунта сильнее, списки и `groups` заменяются целиком. Слияние — штатным `mergeAccountConfig` SDK, как у каналов ядра. Не наследуются опции одного бота: `botToken`, `tokenFile`, `name`, `transport`, `webhookUrl`, `webhookSecret`, `webhookSecretFile`, `webhookPath`. `channels.max.enabled: false` выключает и именованные аккаунты. Конфиг с одним аккаунтом на верхнем уровне работает как прежде.
- Из JSON-схемы канала и zod-схемы убраны `default` (`dmPolicy`, `groupPolicy`, `mediaMaxCount`, `actionScope`, `notify`, `disableLinkPreview`): gateway записывает умолчания схемы в конфиг, в том числе в `accounts.<id>`, и они перекрывали значение канала (из-за этого наследование `notify`, `disableLinkPreview`, `mediaMaxCount` не работало вживую). Умолчания применяются в коде при чтении и не изменились; `channels.defaults.groupPolicy` ядра теперь учитывается, когда `groupPolicy` не задан ни у аккаунта, ни у канала.

### Security

- Локальные файлы для исходящих отправок читаются только через политику доступа к медиа ядра. Раньше `uploadMedia` делал `fs.readFile` для любого пути, а действия `send`/`sendAttachment`, адаптер исходящих и доставка ответа агента игнорировали `mediaLocalRoots`, `mediaReadFile` и `mediaAccess`; для `send` ядро путь не проверяет, для `sendAttachment` — только первый источник. Теперь каждый локальный источник (включая каждый элемент `attachments[]`) идёт через загрузчик SDK `loadWebMediaRaw` с опциями `buildOutboundMediaLoadOptions`: только внутри разрешённых каталогов (сверка по `realpath`, выход через `..` и symlink закрыт), через `mediaReadFile`, если ядро его передало, с лимитом `mediaMaxMb`. Корни — те, что передало ядро; без них — `getAgentScopedMediaLocalRoots` (media-каталоги gateway и рабочий каталог агента). Путь вне корней даёт ошибку `Local media path is not under an allowed directory: …`, файл не читается; для нескольких вложений отказанные попадают в `mediaErrors`, остальные уходят. `MaxApi.uploadMedia` принимает только байты. В `describeMessageTool` объявлены `mediaSourceParams` для `send` и `sendAttachment`.
- Действия инструмента `message` ограничены чатами, которые допускает политика канала (`actionScope`, по умолчанию `admitted`). Раньше `edit`, `delete`, `pin`, `unpin`, `sticker`, `sendAttachment` и `send` выполнялись в любом чате: ядро проверяет чужие чаты только при ужесточённом `tools.message.crossContext` (оба флага по умолчанию разрешают), а `edit`/`delete` по одному `messageId` не проверяет никогда — инъекция в одном чате могла править и удалять сообщения в другом. Теперь чат действия определяется по цели (`user:<id>` — диалог, отрицательный id — группа, положительный — `GET /chats`) или по сообщению (`GET /messages/{mid}`), сравнивается с текущим чатом хода и проверяется теми же правилами, что и входящие (правила вынесены в общий модуль `access-policy.ts`). Отказ — ошибка инструмента `ToolAuthorizationError` с причиной, до любого изменения в MAX; не удалось определить чат — отказ (fail-closed). Вызовы оператора без разговора (CLI, RPC gateway, Control UI) не ограничиваются.
- Списки отправителей в группах действуют: `groups.<id>.allowFrom` (или запись `"*"`), иначе `groupAllowFrom` — первый непустой список; сообщение, нажатие кнопки и команда в допущенной группе проходят только от перечисленных `user_id` (`"*"` — любой, префикс `max:` допустим), вложения недопущенного отправителя не скачиваются; действия инструмента `message` в группе (`actionScope`) требуют, чтобы в список входил и автор запроса. Без списков поведение прежнее. В отличие от Telegram/WhatsApp ядра, `allowFrom` личных сообщений на группы не переносится. Раньше списки были объявлены в схеме и упомянуты в предупреждении безопасности, но к сообщениям групп не применялись.
- Текст сообщений больше не пишется в логи: debug-записи о входящем сообщении и правке содержат тип, длину текста (`textLength`) и идентификаторы, без текста, подписей и транскриптов. Новая необязательная опция `logMessagePreview` (канал и `accounts.<id>`, по умолчанию `false`) возвращает превью 50 символов для отладки. Раньше превью входящего (50 символов) и полный текст правки попадали в лог уровня debug.
- Удалённые медиа скачиваются в память через `runtime.channel.media.fetchRemoteMedia` ядра (`readRemoteMediaBuffer` → `fetchWithSsrFGuard`, строгий режим) без временного файла; картинка передаётся в MAX ссылкой только для публичного https-хоста (не приватный, не loopback, не link-local и не metadata-адрес, в том числе после DNS-разрешения), иначе скачивается и загружается.

### Fixed

- Ответ агента на нажатие кнопки больше не теряет медиа: текст и клавиатура по-прежнему отвечают на нажатие (`POST /answers`), а картинки, файлы и голосовое того же ответа уходят в чат следом. Сбой ответа на нажатие не мешает отправке медиа; ошибка после видимой части — частичная доставка по контракту SDK. Раньше доставка завершалась на ответе на нажатие, и медиа, включая голосовое TTS, молча пропадало.

## 0.7.1 - 2026-09-26

### Fixed

- Webhook-режим больше не глохнет с `GatewayDrainingError: Gateway is draining; new tasks are not accepted`. Gateway выдаёт обработчику HTTP-роута допуск работы (root-work admission в `AsyncLocalStorage`) только на время запроса и освобождает его в `finally` после ответа; обработка апдейта, запущенная после ответа `200` из того же async-контекста, наследовала освобождённый допуск, и запуск агента/сессии отвергался как «draining», хотя gateway работал. Теперь обработчик роута после проверки секрета, тела и дубликата только кладёт апдейт в очередь аккаунта (`webhook-queue.ts`), а задача аккаунта — она стартует вне любого запроса, как цикл polling, — забирает апдейты и вызывает `dispatchUpdate` в своём контексте: внутри чата строго по порядку, между чатами параллельно, не больше 4. Ошибки обработки логируются, цикл не падает. При остановке аккаунта начатые апдейты дорабатывают (ожидание до 3 с), принятые, но не начатые передаются следующему старту того же аккаунта в процессе (MAX их не повторит); очередь ограничена 5000 апдейтами. Тесты: `AsyncLocalStorage`-модель допуска (dispatch идёт в контексте задачи аккаунта, а не запроса, в том числе сквозь `handleMaxWebhookRequest`), порядок в чате, лимит параллельности, abort и передача остатка.
- Цели `user:<id>` (и `max:user:<id>`) проходят нормализацию справочника канала: раньше `normalizeTarget`/`looksLikeId` принимали только числа, `message` с `target: "user:4260364"` доходил до плагина как `4260364` → `chat_id` → `dialog.not.found`. Кроме того, если голое положительное число как `chat_id` получает `dialog.not.found`/`chat.not.found`, отправка один раз повторяется как `user_id` (первая попытка не доставлена, дубля нет).
- Инструмент `message`: `send` и `sendAttachment` с несколькими `attachments[]` отправляют все вложения через `sendMaxMediaGroup` (изображения/видео альбомами до 12, аудио и файлы по одному, порядок сохраняется, подпись на первом сообщении) и возвращают `messageIds`; раньше уходило только первое вложение. Частичный сбой не теряет уже отправленное: ошибки — в `mediaErrors`, исключение — только если не ушло ничего.
- Закрепление в диалогах: MAX отвечает на `PUT /chats/{id}/pin` в диалоге `400 proto.payload "Method is not available for dialogs"`. `pinMaxMessage` теперь не вызывает API для диалогов (цель `user:<id>`, `chat_type: "dialog"` у отправленного сообщения или `GET /chats/{id}` для положительного id) и возвращает `pinned: false` с причиной; `pinDeliveredMessage` и ответы агента с `delivery.pin` в диалоге больше не пишут ERROR, действие `pin` и `send` с `pin` возвращают `pinned: false` (`reason`/`pinSkipped`). Заменяет поведение 0.7.0 «chat id диалога из `GET /messages/{mid}`».

## 0.7.0 - 2026-09-26

### Added

- `capabilities.unsend` и `capabilities.reply` (`DELETE /messages` и ответы через `link.type=reply` уже поддерживались, но не объявлялись).
- Webhook-ingress на HTTP-сервере gateway: роут регистрируется из жизненного цикла аккаунта через `registerPluginHttpRoute` (`plugin-sdk/webhook-ingress`: `auth: "plugin"`, `match: "exact"`, `pluginId`/`source`, `replaceExisting`, `throwOnFailure`) и обслуживается `handleMaxWebhookRequest`. Путь — `webhookPath`, иначе pathname `webhookUrl`, иначе `/max/webhook` (раньше `/max`). Секрет `X-Max-Bot-Api-Secret` сверяется timing-safe до чтения тела (401), тело без `update_type` — 400, валидное обновление получает 200 сразу, обработка идёт асинхронно с логированием ошибок (раньше ответ ждал `onUpdate` и при ошибке отдавал 500, провоцируя повторы MAX). Повторные доставки отсекаются LRU на 1000 ключей `(update_type, timestamp, mid|callback_id)`. Тесты: регистрация роута с mock, 200/400/401/405, дедупликация, сквозной прогон через настоящий `node:http` и `fetch`.
- Режимы транспорта `transport: "polling" | "webhook"` (по умолчанию `webhook`, если задан `webhookUrl`, иначе `polling`). В webhook-режиме polling не запускается: после регистрации роута плагин делает `GET /subscriptions`, удаляет подписки этого бота на другие URL и вызывает `POST /subscriptions {url, update_types, secret}`; при остановке подписка сохраняется, чтобы рестарт не терял события (снимается переходом на `polling` или вручную `DELETE /subscriptions?url=`). В polling-режиме активная подписка (при ней MAX не отдаёт `GET /updates`) удаляется с предупреждением. Статус webhook-аккаунта публикуется без `lastTransportActivityAt`, как у Telegram webhook, чтобы тихий канал не считался stale-socket. Секрет: `webhookSecret`, новый `webhookSecretFile` (обычный файл, не symlink) или сгенерированный один раз и сохранённый в state-файле аккаунта; формат проверяется по схеме MAX (5–256 символов `[A-Za-z0-9_-]`). Схема конфига и `openclaw.plugin.json`: `transport`, `webhookSecretFile`, `transport="webhook"` требует `webhookUrl`; тест сверяет поля манифеста с zod-схемой.
- README: раздел «Webhook» — требования MAX (HTTPS:443, 200 за 30 с, до 10 повторов, автоотписка через 8 часов, секрет в заголовке, при подписке не работает long polling), устройство роута и подписки, конфиг для этой установки (`https://max.kotbanzai.com/max/webhook`, секрет файлом), порядок включения (сначала деплой и рестарт с новым кодом в polling-режиме) и откат; обновлены таблица полей и SKILL.md.
- Контракт `presentation` в исходящем пути: адаптер объявляет `presentationCapabilities` (кнопки, select, context, divider, таблицы и графики; лимиты MAX: текст кнопки ≤128, payload ≤1024 байт, ≤30 рядов, ≤210 кнопок, текст ≤4000) и `renderPresentation`: title/tone → жирный заголовок с эмодзи тона, text/context/divider → MAX markdown, table/chart → моноширинный блок, `buttons` → `inline_keyboard` по 3 в ряд (url и web-app с URL → `link`; command/callback/approval/question → `callback` с приватным payload), `select` → ряды callback-кнопок по 2; неотрисованные кнопки остаются подписями в тексте. `sendPayload` режет текст длиннее 4000 символов (клавиатура на последнем куске) и сам рендерит payload, если presentation дошла до него неотрисованной; ответы агента (`deliverMaxReply`) проходят ту же политику через `renderPresentationForDelivery`. `delivery.pin`: `deliveryCapabilities.pin` + `pinDeliveredMessage` → `PUT /chats/{chatId}/pin` c проверкой `assertDirectAdapterHandoff` перед каждым запросом; для `user:<id>` chat id диалога берётся из `GET /messages/{mid}`. Ответ агента с `delivery.pin` закрепляет первое доставленное сообщение.
- Обратный путь presentation-кнопок на `message_callback`: approval → `resolveApprovalOverGateway` с явным `approvalKind` (`plugin-sdk/approval-gateway-runtime`), вариант `ask_user` → `questionGatewayRuntime.resolveOption` (`plugin-sdk/question-gateway-runtime`), итог — всплывающее уведомление через `POST /answers`. Нажимать approval могут только отправители, явно перечисленные в `allowFrom` (для вопросов достаточно `*`). Command-кнопка возвращается текстом команды и идёт штатным путём нативных команд; непрозрачный callback приходит агенту как `callback_data: <value>` и не разбирается как slash-команда. Payload обычных `channelData.max.buttons` по-прежнему приходит текстом без изменений. Тесты round-trip: рендер → нажатие в форме живой фикстуры → `dispatchUpdate`.
- Расшифровка голосовых от MAX: если у аудио-вложения есть `transcription` (сосед `payload` в `AudioAttachment`), агент получает `[Voice transcript: …]` в тексте, а медиа-факт помечается `transcribed: true` (`ChannelInboundMediaInput`), чтобы ядро не запускало STT повторно. Файл по-прежнему скачивается; без расшифровки (`null`, пусто) — прежний путь через STT ядра.
- Webhook-режим сверяет подписку раз в 12 минут (`GET /subscriptions`): если MAX снял её после 8 часов недоставки, плагин пересоздаёт `POST /subscriptions` с тем же секретом и списком событий и пишет warning; сетевые ошибки проверки только логируются, проверка не запускается внахлёст, таймер снимается при остановке аккаунта. Раньше после такой отписки события не приходили до рестарта gateway.
- Альбомы и картинки по ссылке. `sendMaxMediaGroup` отправляет несколько медиа минимумом сообщений: подряд идущие изображения и видео — одним сообщением до 12 штук (лимит docs «Медиафайлы»), аудио и файлы — по одному (MAX не сочетает файл с фото/видео); порядок сохраняется, подпись и reply — на первом сообщении, клавиатура — на последнем. Используется в ответах агента (`deliverMaxReply`, раньше каждая картинка — отдельное сообщение) и в `outbound.sendPayload` (раньше из `mediaUrls` отправлялся только первый элемент). https-ссылки на изображения уходят как `image.payload.url` без скачивания и загрузки; если MAX отвергает сообщение (`MaxApiError`), ссылки скачиваются, загружаются через `POST /uploads` и сообщение отправляется ещё раз. Прочие удалённые URL (http/https, не картинки) скачиваются во временный файл и загружаются — раньше `sendMaxMediaMessage`/`sendMedia` пытались прочитать URL как локальный путь. `sendMaxMediaMessage` сохранил сигнатуру, добавлена опция `mediaMaxBytes` (из `mediaMaxMb` аккаунта).
- Точка входа для setup-режима `setup-entry.ts` (`defineSetupPluginEntry`, `openclaw.setupEntry: ./dist/setup-entry.js`): OpenClaw грузит её вместо полной, когда канал выключен или не настроен.

Запросы снимаются с настоящих send/subscribe через mock `fetch`. Снимок обновляется `npm run schema:update [ref]`.
- `npm run check:cycles` — проверка циклических импортов между модулями `src/` (в CI).

### Fixed

- Совместимость с OpenClaw 2026.9.3: конфиг читается через `config.current()` / `replaceConfigFile` (в рантайме плагинов убраны `loadConfig`/`writeConfigFile`), с откатом на старый API. Раньше исходящая отправка через `outbound.sendText/sendPayload` падала с `config.loadConfig is not a function`.
- Тесты на OpenClaw 2026.9.6 снова зелёные. `dmPolicy`/`groupPolicy` с дефолтами строятся на zod самого плагина: обёртка `.optional().default()` над enum-ами SDK ломалась («expected nonoptional»), когда плагин и gateway подтягивали разные копии zod (4.4 в каталоге плагина против 4.6 у gateway); значения сверяются с SDK тестом. Заглушка `IncomingMessage` в webhook-тестах получила `socket`, как у настоящего запроса.
- Команды бота регистрируются через `PATCH /me/commands` с телом `{commands:[…]}`: прежний `PATCH /me` MAX отвечает 404 `method.not.found`, так что `channels.max.commands` фактически не применялись. Удалены `MaxBotPatch` и `editMyInfo`; `setMyCommands` возвращает `BotCommandsInfo`.
- `message_callback`: плагин брал `callback.message`, которого в API нет (`message` — сосед `callback` в апдейте), поэтому ответ на нажатие кнопки уходил в `{chat_id: user_id}` вместо реального чата диалога/группы. Теперь recipient берётся из `update.message.recipient`, откат на пользователя — только если сообщение с клавиатурой удалено (`message: null`); `user_locale` пробрасывается. Нажатие кнопки бота в группе считается обращением к боту и не отсекается требованием упоминания. Типы `MessageCallbackUpdate`/`MaxCallback` приведены к схеме; тесты на живой фикстуре (DM) и групповой recipient.
- Цели `@username` и ссылки max.ru больше не резолвятся через `GET /chats/{link}`: такого варианта нет в схеме, живой вызов отвечает `chat.not.found`. `resolveMaxTarget` сразу бросает понятную ошибку («MAX API does not resolve @username … use a numeric chat_id … or user:<id>») без запроса к API; `MaxApi.getChat` принимает только числовой id. SKILL.md обновлён.
- Edit-стриминг (`streamMode: "partial"`) больше не теряет кнопки финального ответа: `editMaxMessage` принимает `buttons` и передаёт `inline_keyboard` в `attachments` `PUT /messages` (без кнопок поле не отправляется — по схеме `null`/отсутствие сохраняет текущие вложения, пустой список их удаляет). Финальная правка черновика делается и при неизменном тексте, если есть кнопки; медиа финального ответа уходят без повторной клавиатуры.
- Временные файлы медиа: имя скачанного файла больше не подставляется в путь как есть (`/tmp/max-media-<ts>-${fileName}` позволял `../` и разделители из имени, пришедшего от удалённого сервера). Новая `withRemoteMediaTempFile` (`src/media-temp.ts`) — единая функция «скачать во временный файл»: загрузка через `fetchRemoteMedia` с лимитом `mediaMaxMb`, приватный каталог `mkdtemp`, файл `0600`, удаление каталога в `finally`; её используют ответы агента и действие `send`. `sanitizeMaxFileName` оставляет один сегмент пути без `..`, управляющих и зарезервированных символов, ограничивает длину 120 символами с сохранением расширения и добавляет расширение по `contentType`; им же чистится имя входящего вложения, которое уходит агенту и в `saveMediaBuffer`. Тесты на опасные имена и очистку при ошибке.
- Входящие вложения скачиваются только после проверок DM (allowlist/pairing) и групп (allowlist, упоминание): медиа из игнорируемых сообщений больше не тратят трафик и место на диске, `getVideoInfo` для них не вызывается. Тесты на группу вне allowlist, сообщение без упоминания и DM от чужого отправителя.
